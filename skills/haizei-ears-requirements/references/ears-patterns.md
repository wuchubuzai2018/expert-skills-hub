# EARS 模式参考

EARS（Easy Approach to Requirements Syntax，需求语法简易方法）定义了 6 种句式模式，用于消除规格说明中的歧义。每种模式都通过特定关键字，明确触发条件与期望行为。

以下模板中的关键字和 `shall` 保留原始英文写法，以确保 EARS 语法表达准确。

---

## 模式 1：Ubiquitous（普适型）

**模板**：`系统 shall <响应>.`

**适用场景**：行为始终生效，没有触发事件，也没有前置条件。普遍适用。

**关键字**：无（不使用 WHEN / WHILE / IF / WHERE）。

**示例**：
- 系统 shall 使用 AES-256 对静态数据进行加密。
- API shall 使用 JSON 格式返回响应。
- 系统 shall 记录所有认证尝试，并包含时间戳、用户 ID 和结果。

**常见错误**：
- 实际存在触发事件时却使用普适型 → 应改用 Event-driven。
- 将多个行为写在同一条陈述中 → 应拆分成多条规格。

---

## 模式 2：Event-Driven（事件驱动型）

**模板**：`WHEN <触发事件>, 系统 shall <响应>.`

**适用场景**：行为由某个具体且可检测的事件触发。

**关键字**：`WHEN`

**示例**：
- WHEN 用户点击“提交”按钮时，系统 shall 校验所有表单字段。
- WHEN 新订单创建完成时，系统 shall 向客户发送确认邮件。
- WHEN 会话令牌过期时，系统 shall 将用户重定向到登录页。
- WHEN 文件上传完成时，系统 shall 显示持续 5 秒的成功提示。

**常见错误**：
- 将事件和状态混淆（事件是瞬时的，状态是持续的）→ 对持续条件应使用 State-driven。
- 省略具体触发事件 → `WHEN something happens` 过于模糊。

---

## 模式 3：State-Driven（状态驱动型）

**模板**：`WHILE <状态>, 系统 shall <响应>.`

**适用场景**：只要某个条件持续成立，该行为就持续适用。

**关键字**：`WHILE`

**示例**：
- WHILE 系统处于维护模式时，系统 shall 向所有用户展示维护页面。
- WHILE 电池电量低于 20% 时，设备 shall 禁用后台同步。
- WHILE 用户处于免费套餐时，系统 shall 将单个文件上传大小限制为 10 MB。
- WHILE 网络连接不可用时，应用 shall 将待发请求保存在本地队列中。

**常见错误**：
- 将 WHILE 用于一次性事件 → 离散触发应使用 WHEN。
- 状态定义含糊 → 应明确状态的进入条件和退出条件。

---

## 模式 4：Unwanted Behavior（非期望行为型）

**模板**：`IF <条件>, THEN 系统 shall <响应>.`

**适用场景**：处理错误条件、故障、边界场景或不希望发生的情况。

**关键字**：`IF ... THEN`

**示例**：
- IF 数据库连接失败时，THEN 系统 shall 以 5 秒间隔重试连接 3 次。
- IF 用户输入的邮箱格式无效时，THEN 系统 shall 显示“请输入有效的邮箱地址”。
- IF 支付网关返回错误时，THEN 系统 shall 将订单标记为支付失败。
- IF 可用磁盘空间低于 1 GB 时，THEN 系统 shall 向运维团队发送告警。

**常见错误**：
- 将 IF-THEN 用于正常流程 → 对预期事件应使用 WHEN。
- 缺少明确恢复动作 → `处理错误` 不是有效响应。

---

## 模式 5：Optional Feature（可选功能型）

**模板**：`WHERE <功能已启用>, 系统 shall <响应>.`

**适用场景**：该行为仅在某个特定功能或配置启用时适用。

**关键字**：`WHERE`

**示例**：
- WHERE 已启用双因素认证时，系统 shall 在密码输入后要求一次性验证码。
- WHERE 高级套餐已生效时，系统 shall 允许无限制上传文件。
- WHERE 无障碍模式已启用时，系统 shall 为所有图片提供读屏描述。
- WHERE 审计日志模块已安装时，系统 shall 记录所有数据修改事件。

**常见错误**：
- 在功能始终存在时使用 WHERE → 应改用 Ubiquitous。
- 将 WHERE 与 WHILE 混淆（WHERE 表示功能开关；WHILE 表示运行时状态）。

---

## 模式 6：Complex（复合型）

**模板**：组合使用模式 2 至模式 5 的关键字。

**适用场景**：行为需要同时满足多个条件，例如事件 + 状态、事件 + 功能开关等。

**示例**：

**WHILE + WHEN（状态 + 事件）**：
- WHILE 系统处于离线模式时，WHEN 用户新建记录时，系统 shall 将记录写入本地待同步队列。

**IF + WHEN（异常条件 + 事件）**：
- IF 用户已超过限流阈值时，THEN WHEN 用户发送新的 API 请求时，系统 shall 返回带有 Retry-After 头的 HTTP 429 响应。

**WHERE + WHEN（功能开关 + 事件）**：
- WHERE 已启用推送通知时，WHEN 收到新消息时，系统 shall 显示包含发送者姓名和消息摘要的推送通知。

**WHERE + IF（功能开关 + 异常条件）**：
- WHERE 已启用自动保存功能时，IF 应用发生崩溃时，THEN 系统 shall 在下次启动时恢复最近一次自动保存的版本。

**常见错误**：
- 组合过多关键字导致表达过于复杂 → 如果需要超过 2 个关键字，应考虑拆分为多条规格。
- 关键字顺序不正确 → 应保持逻辑顺序：WHERE / WHILE → WHEN / IF → shall。

---

## 模式选择流程图

```
是否存在触发事件？
├── 是：是否还存在持续条件？
│   ├── 是 → 复合型（WHILE + WHEN）
│   └── 否 → 事件驱动型（WHEN）
├── 否：是否存在持续条件？
│   ├── 是 → 状态驱动型（WHILE）
│   └── 否：是否属于错误 / 故障场景？
│       ├── 是 → 非期望行为型（IF-THEN）
│       └── 否：是否依赖可选功能？
│           ├── 是 → 可选功能型（WHERE）
│           └── 否 → 普适型
```

## 关键字汇总

| 关键字 | 含义 | 触发类型 |
|---------|---------|-------------|
| （无） | 始终适用 | 无条件 |
| WHEN | 在事件发生时 | 离散事件 |
| WHILE | 在某状态持续期间 | 持续条件 |
| IF...THEN | 在非期望条件发生时 | 错误 / 边界场景 |
| WHERE | 在功能 / 配置启用时 | 功能开关 |
| 组合使用 | 多个条件组合 | 复合型 |


## 反模式

| 反模式 | 问题 | EARS 改写后 |
|-------------|---------|-----------------|
| 系统应该足够快。 | `should` 语气太弱；`足够快` 含义模糊 | 系统 shall 在 95 分位上于 200 ms 内返回查询结果。 |
| 妥善处理错误。 | `处理` 和 `妥善` 都很模糊 | IF API 返回 HTTP 5xx 时，THEN 系统 shall 以指数退避策略重试 3 次。 |
| 系统支持导出 PDF。 | `支持` 表述不明确 | WHEN 用户选择“导出 PDF”时，系统 shall 在 3 秒内生成并开始下载 PDF 文件。 |
| 用户会收到通知。 | 被动语态；无触发条件；无细节 | WHEN 文档被更新时，系统 shall 在 2 分钟内向所有订阅用户发送邮件通知。 |
| 系统能处理并发用户。 | 缺少可衡量标准 | 系统 shall 支持最多 10,000 个并发会话，且平均响应时间低于 500 ms。 |
| WHEN X, IF Y, WHILE Z, 系统 shall ... | 关键字过多 | 拆分为多条规格，且每条规格最多使用 2 个关键字。 |
