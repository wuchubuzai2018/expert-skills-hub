# EARS 写作与校验规则

该文档用于在改写完成后检查规格写法是否统一、是否可测试、是否存在模糊表达或结构问题。

## 编写规则

1. **每条规格只允许一个 `shall`**。如果两个动作之间需要用 `and` 连接，应拆分为两条规格。
2. **EARS 关键字必须大写**：WHEN、WHILE、IF、THEN、WHERE。
3. **`shall` 表示强制要求**，**`may` 表示可选要求**。不要使用 `should`、`could` 或 `might`。
4. **使用主动语态**：应写成 `系统 shall 显示...`，而不是 `错误被显示...`。
5. **响应必须可衡量**：应包含数量、时间限制、格式或其他可验证标准。
6. **触发条件必须具体**：避免使用 `when something happens` 或 `if there is a problem` 这类模糊条件。
7. **一条需求一个主语**：系统 / 子系统名称应明确，不要省略真正执行动作的主体。
8. **优先使用可测试动词**：显示、记录、发送、存储、校验、拒绝、启用、禁用、限制、告警等优先于“处理、支持、优化”。
9. **数值约束尽量定量化**：如响应时间、重试次数、容量上限、提示时长等，能量化就不要只写“尽快”或“较快”。
10. **避免无必要的实现细节**：除非实现方式本身就是业务契约，否则应描述系统响应，而非内部技术实现。
11. **中文条件短语保持统一**：状态用“在…时”，事件用“当…时”，异常用“如果…，则…”，功能开关用“当系统包含…”或“在已启用…时”。

## 典型处理策略

- **多个异常并列**：分别拆成多条不期望行为需求，不要把多种错误塞在一个 IF 里。
- **一个句子多个动作**：优先拆分；只有动作强耦合、拆开会丢失语义时，才保留复合模式。
- **状态前后行为切换**：通常拆成“状态驱动 + 事件驱动”两条，比写成一条复杂模式更清晰。
- **性能或时效要求模糊**：把“快一点、及时、尽快”改成可测量的 SLA 或时间上限；若无依据，则列为待确认问题。
- **AI 提示词低命中**：优先把自然语言需求先改成 EARS 规格，再用于后续代码生成、测试设计或规则审查。

## 完成标准

- 每条规格都能明确归类到某一种 EARS 模式或合法的两关键字复合模式。
- 每条规格只包含一个 `shall`，且响应内容可验证。
- 输出中不存在 `should`、`could`、`might`、`appropriately`、`supports` 这类模糊表达，除非它们出现在“改写前”示例中。
- 如存在未决前提或缺失约束，已显式列出待确认问题。
- 如果用户要求对照输出，已提供改写前 / 改写后结果。
