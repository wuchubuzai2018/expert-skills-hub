# EARS 使用说明

该文档用于说明何时适合使用 EARS、为什么要使用 EARS，以及用户通常会以什么表达触发该技能。

## 为什么使用 EARS

- 开发、测试与产品经常需要 2 到 3 轮口头澄清，才能把需求意图说清楚。
- 自然语言需求里常出现“可以、尽快、支持、优化、合理、友好、自动”等不可验证表达。
- 提示词或需求描述中缺少统一句式时，AI 难以稳定抽取前置条件、触发事件和系统响应。
- 同一个词在不同需求里的含义可能漂移，例如“校验”有时指前端格式检查，有时指后端业务规则。
- 当需求无法清楚套入 EARS 模式时，往往意味着需求本身仍缺少前提、触发或响应定义。

## 快速使用入口

如果目标是把一段原始需求尽快整理成可测试规格，优先按下面顺序执行：

1. 先识别主语、触发条件、状态条件、异常条件和响应动作。
2. 再判断是否存在多个动作、多种异常或多个语义混合在同一句里。
3. 必要时先拆分，再进入 EARS 模式路由表选择句式。
4. 改写后补齐量化约束、失败处理、时间要求和待确认问题。
5. 按统一输出结构给出模式判断、改写结果和改写前后对照。

## 常见触发表达

- 用 EARS 改写这条需求。
- 把这段需求改成 EARS 规格。
- 帮我做 EARS 需求改写。
- 看看这条需求该用哪种 EARS 模式。
- 审查这组需求是否符合 EARS。

## 何时使用（Use When）

- 需要把自然语言需求、会议纪要或口头描述改写为正式规格说明。
- 需要判断一条规格应使用 WHEN、WHILE、IF...THEN、WHERE 还是无关键字句式。
- 需要审查现有规格是否存在模糊词、隐含条件、不可验证响应或多个动作挤在一条里的问题。
- 需要在 USDM 的 SPEC 层统一规格写法，确保不同作者输出的规格风格一致。
- 需要把英文 EARS 模板本地化为中文语境，但仍保留 EARS 关键字和 `shall`。

## 典型使用场景

- 将 PRD、原型备注、需求评审纪要中的一句话需求改写为可测试规格。
- 为研发、测试、产品三方评审准备“改写前 / 改写后”的对照版本，降低理解偏差。
- 对已有规格做质量审查，找出模糊词、缺失触发条件、不可验证响应和多动作混写问题。
- 将验收标准、接口约束、异常处理要求整理为统一风格的规格条目。
- 在编写测试用例之前，先把需求整理成 EARS 规格，减少测试输入本身的歧义。
- 在 USDM 或内部规格体系中，把 SPEC 层内容统一成可追踪、可评审、可验收的句式。

## 不适用场景

- 仅需要做文学润色、营销文案优化或普通语句美化，而不要求形成可测试规格。
- 需求本身尚未明确到可判断触发条件、状态或响应的程度，此时应先补业务背景和约束。
- 需要输出完整需求文档结构、原型说明、流程图或领域建模，而不仅是规格改写。
