# EARS 改写示例

以下示例展示了如何将模糊的规格说明改写为符合 EARS 模式的规格说明。

以下示例中的 EARS 关键字和 `shall` 保留原始英文写法，以确保句式语法准确。

补充说明：以下每组示例同时保留“标准 EARS 写法”和“中文生产写法”。实际生产输出默认优先使用中文生产写法。

---

## Ubiquitous（普适型）

**改写前**：系统应该安全地存储数据。
**标准 EARS 写法**：系统 shall 使用 AES-256-GCM 对所有存储数据进行加密。
**中文生产写法**：系统应使用 AES-256-GCM 对所有存储数据进行加密。

**改写前**：所有 API 错误响应都要带错误码。
**标准 EARS 写法**：API shall 在每个错误响应体中包含错误码和人类可读的错误信息。
**中文生产写法**：API 应在每个错误响应体中包含错误码和人类可读的错误信息。

---

## Event-Driven（事件驱动型，WHEN）

**改写前**：用户可以重置密码。
**标准 EARS 写法**：WHEN 用户点击“重置密码”并提交已注册邮箱时，系统 shall 发送一个 30 分钟内有效的密码重置链接。
**中文生产写法**：当用户点击“重置密码”并提交已注册邮箱时，系统应发送一个 30 分钟内有效的密码重置链接。

**改写前**：系统会把新注册用户通知管理员。
**标准 EARS 写法**：WHEN 新用户完成注册时，系统 shall 在 1 分钟内向管理员邮件组发送通知邮件。
**中文生产写法**：当新用户完成注册时，系统应在 1 分钟内向管理员邮件组发送通知邮件。

---

## State-Driven（状态驱动型，WHILE）

**改写前**：系统会限制试用用户的功能。
**标准 EARS 写法**：WHILE 用户处于试用套餐时，系统 shall 将 API 调用限制为每天 100 次。
**中文生产写法**：在用户处于试用套餐时，系统应将 API 调用限制为每天 100 次。

**改写前**：文件上传时显示进度条。
**标准 EARS 写法**：WHILE 文件上传进行中时，系统 shall 显示反映已传输字节百分比的进度条。
**中文生产写法**：在文件上传进行中时，系统应显示反映已传输字节百分比的进度条。


---

## Unwanted Behavior（非期望行为型，IF-THEN）

**改写前**：网络错误要妥善处理。
**标准 EARS 写法**：IF API 请求因网络超时失败时，THEN 系统 shall 以指数退避方式重试最多 3 次（1 秒、2 秒、4 秒）。
**中文生产写法**：如果 API 请求因网络超时失败，则系统应以指数退避方式重试最多 3 次（1 秒、2 秒、4 秒）。

**改写前**：要防止重复提交。
**标准 EARS 写法**：IF 用户在提交进行中再次点击提交按钮时，THEN 系统 shall 忽略这次重复点击。
**中文生产写法**：如果用户在提交进行中再次点击提交按钮，则系统应忽略这次重复点击。


---

## Optional Feature（可选功能型，WHERE）

**改写前**：系统支持双因素认证。
**标准 EARS 写法**：WHERE 用户已启用双因素认证时，系统 shall 在密码验证通过后要求输入 6 位 TOTP 验证码。
**中文生产写法**：在已启用双因素认证时，系统应在密码验证通过后要求输入 6 位 TOTP 验证码。

**改写前**：高级用户有更多存储空间。
**标准 EARS 写法**：WHERE 高级套餐已生效时，系统 shall 允许每个账户最多存储 100 GB 文件。
**中文生产写法**：在高级套餐已生效时，系统应允许每个账户最多存储 100 GB 文件。

---

## Complex（复合型）

**改写前**：离线用户也应该可以继续工作，之后再同步。
**标准 EARS 写法**：WHILE 系统处于离线模式时，WHEN 用户新建记录时，系统 shall 将记录写入本地待同步队列。 WHEN 网络恢复连接时，系统 shall 在 30 秒内完成所有待同步记录的同步。
**中文生产写法**：在系统处于离线模式时，当用户新建记录时，系统应将记录写入本地待同步队列。当网络恢复连接时，系统应在 30 秒内完成所有待同步记录的同步。

**改写前**：被限流的用户应该看到合适的错误提示。
**标准 EARS 写法**：IF 用户已超过限流阈值时，THEN WHEN 用户发送新的 API 请求时，系统 shall 返回带有 `Retry-After` 头的 HTTP 429 响应，头值为剩余冷却秒数。
**中文生产写法**：如果用户已超过限流阈值，则当用户发送新的 API 请求时，系统应返回带有 `Retry-After` 头的 HTTP 429 响应，头值为剩余冷却秒数。

## 反模式对照表

| 反模式 | 问题 | 改写后版本 |
|-------------|---------|-------------------|
| 系统应该足够快。 | `should` 语气弱；`足够快` 含义模糊 | 系统应在 95 分位上于 200 ms 内返回搜索结果。 |
| 妥善处理错误。 | `处理` 和 `妥善` 都很模糊 | 如果数据库查询失败，则系统应返回 HTTP 503。 |
| 系统支持导出 PDF。 | `支持` 表述不明确 | 当用户点击“导出 PDF”时，系统应在 3 秒内生成 PDF 并开始下载。 |
| 用户会收到变更通知。 | 被动语态掩盖了行为主体和触发条件 | 当协作者修改文档时，系统应在 2 分钟内向所有订阅用户发送邮件通知。 |
| 系统应该能处理并发用户。 | 缺少可衡量标准 | 系统应支持最多 10,000 个并发用户会话，且平均响应时间不超过 500 ms。 |
