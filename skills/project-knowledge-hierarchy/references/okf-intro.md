# Google OKF（Open Knowledge Format）介绍

## 用途

本文档介绍 Google Cloud 在 2026 年发布的 **OKF（Open Knowledge Format，开放知识格式）** 规范，并说明本技能（project-knowledge-hierarchy）与 OKF 的对应关系与借鉴点，供 AI 在用户询问"是否对齐 OKF"、"如何兼容 OKF"时加载。

> 加载说明：SKILL.md 仅在"是否对齐 OKF"问题被触发时引用本文件，详细内容按需加载。

## 1. OKF 是什么

**全称**：Open Knowledge Format（开放知识格式）

**官方定义（一句话）**：

> OKF is an open, human- and agent-friendly format for representing knowledge: the metadata, context, and curated insight that surrounds data and systems. It is designed to be authored by people, generated by agents, exchanged across organizations, and consumed by both.

**核心定位**：

- 是一套**目录级 Markdown 约定** + **小而严格的 YAML frontmatter 契约**
- 不是文件格式、不是 Schema Registry、不是运行时、不是查询语言
- **为人类与 AI 智能体共同消费而设计**，强调"agent-maintained corpus"
- **可移植、可交换、Git 原生**：随 git 版本化、随 PR 评审

**版本与许可**：

| 项 | 值 |
|----|----|
| 当前版本 | v0.2（2026-07-25 发布） |
| 初版 | v0.1（2026-06-13） |
| 许可 | Apache-2.0 |
| 规范仓库 | <https://github.com/GoogleCloudPlatform/open-knowledge-format> |
| 规范文件 | [`SPEC.md`](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md) |
| 发布博客（v0.1） | <https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing> |
| 发布博客（v0.2） | <https://cloud.google.com/blog/products/data-analytics/okf-v0-2-adds-trust-signals> |

## 2. OKF 的核心设计思想

### 2.1 "Knowledge Bundle"（知识包）

OKF 把一个目录称为一个 **Knowledge Bundle**：

```
my_bundle/
├── index.md              # 可选。目录索引（OKF 规范 §8）
├── log.md                # 可选。变更历史（OKF 规范 §9）
├── concept-a.md          # 一个概念文件
└── subdir/
    ├── index.md
    └── concept-b.md
```

- 目录结构本身是**领域无关**的，由生产者自由组织
- 只有**两个保留文件名**（`index.md` / `log.md`），没有第三个

### 2.2 仅两个保留文件名

| 文件名 | 用途 |
|--------|------|
| `index.md` | 目录索引，渐进式披露入口。**唯一允许在 frontmatter 中使用 `okf_version` 键的文件** |
| `log.md` | 按日期分组的变更历史 |

> 严格的"两个保留名"是 OKF 保持规范精简的关键设计。

### 2.3 宽容一致性（Permissive Conformance）

OKF 的 §11 明确规定，消费者**不得**因以下原因拒绝一个 Bundle：

- 缺少可选字段
- `type` 取未知值
- 多余的 frontmatter 键
- 损坏的交叉链接
- 缺少 `index.md`

**唯一会硬性拒绝的两种情况**：

1. 非保留 `.md` 文件没有可解析的 YAML frontmatter
2. frontmatter 缺少非空 `type` 字段

> 这是"宽松解析、严格核心"的设计哲学。

### 2.4 信任是一等公民（v0.2 重点）

v0.1 的隐含信任假设："是人类写的"。一旦 agent 一夜生成一万篇文档，这个假设崩塌。

v0.2 把**信任、来源、新鲜度、生命周期、证明**全部提升为 frontmatter 一等字段：

| 族 | 字段 | 说明 |
|----|------|------|
| 来源（Provenance） | `sources` | `[{id, resource, title, author, usage_count, last_modified}]` |
| 生成 | `generated: {by, at}` | 由谁、何时生成 |
| 验证 | `verified: [{by, at}]` | 是否经人类/机器核验 |
| 生命周期 | `status` | `draft \| stable \| deprecated`（缺省 `stable`） |
| 新鲜度 | `stale_after` | ISO8601 绝对时间戳，`now >= stale_after` 即陈旧 |

**信任层级**（由 frontmatter 推导，**不存储**）：

| 层级 | 推导规则 |
|------|----------|
| `unverified` | 无 `verified` 键 |
| `machine-confirmed` | `verified` 中全是机器 actor |
| `human-reviewed` | `verified` 中至少一个 `human:<id>` |

> 关键设计：**层级由消费者推导而非生产者声明**，避免生产者写一句 `trust_tier: human-reviewed` 就自我认证。

### 2.5 Actor 命名约定

`generated.by` / `verified[].by` 的取值约定：

| 模式 | 示例 | 类别 |
|------|------|------|
| `<producer>/<version>` | `reference_agent/gemini-2.5-pro` | machine |
| `human:<id>` | `human:ahormati` | **human**（提升至 human-reviewed） |
| `process:<id>` | `process:finance-nightly` | machine |

### 2.6 交叉链接的两种形式

| 形式 | 示例 | 推荐度 |
|------|------|--------|
| Bundle 相对（绝对） | `[/tables/customers.md](/tables/customers.md)` | **推荐**（跨目录移动稳定） |
| 相对 | `[neighbor](./other.md)` | 可用 |

消费者**必须容忍**断链（断链 ≠ 格式错误）。

### 2.7 概念 ID 规则

**Concept ID = 文件在 Bundle 内的路径去掉 `.md` 后缀**。

- `tables/orders.md` → ID 为 `tables/orders`
- 在 `verified[].by`、`sources[].id` 中均按此引用

## 3. OKF 的 YAML Frontmatter 规范

### 3.1 字段全表

| 字段 | 必需 | 说明 |
|------|------|------|
| `type` | ✅ **唯一必需** | 概念类型短串（如 `BigQuery Table`、`Metric`、`Playbook`、`API Endpoint`、`Reference`、`Attested Computation`） |
| `title` | 推荐 | 人类可读名称，消费者可从文件名派生 |
| `description` | 推荐 | 单句摘要，用于 `index.md`、搜索摘要、预览 |
| `resource` | 推荐 | 底层资产的规范 URI（表、API 等），抽象概念可省略 |
| `tags` | 推荐 | YAML 字符串列表，用于跨切面分类 |
| `status` | 可选 | `draft \| stable \| deprecated`（缺省 `stable`） |
| `generated` | 可选 | `{by, at}` 生成来源 |
| `verified` | 可选 | `[{by, at}, ...]` 验证记录 |
| `sources` | 可选 | `[{id, resource, title, author, ...}]` 来源列表 |
| `stale_after` | 可选 | ISO8601 绝对时间戳，新鲜度阈值 |

> `index.md` 是唯一允许在 frontmatter 中使用 `okf_version` 键的文件（用于声明目标规范版本）。

### 3.2 正文约定（非强制）

| 标题 | 用途 |
|------|------|
| `# Schema` | 资产列/字段的结构化描述 |
| `# Examples` | 具体使用示例 |
| `# Computation` | 受认可的演算（仅 `Attested Computation`） |

### 3.3 完整示例（v0.2）

````markdown
---
type: BigQuery Table
title: Customer Orders
description: One row per completed customer order across web, mobile, and marketplace channels.
resource: https://bigquery.googleapis.com/v2/projects/acme/datasets/sales/tables/orders
tags: [sales, orders, revenue]
status: stable
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-30T14:00:00Z }
verified:
  - { by: human:kliu@acme, at: 2026-07-01T16:00:00Z }
stale_after: 2026-12-31T00:00:00Z
sources:
  - id: warehouse-schema
    resource: https://wiki.acme.internal/data/warehouse/schemas/sales
    title: Acme Retail warehouse schema — sales dataset
    author: team:data-platform
    usage_count: 1240
    last_modified: 2026-06-15
---
````

## 4. OKF 与同类规范的关系

| 规范 / 约定 | 内容 | 与 OKF 的关系 |
|------------|------|---------------|
| **`llms.txt`**（Answer.AI, 2024） | 网站根目录的单个文本文件 | 单文件、轻量；OKF 解决**结构化知识库**问题 |
| **`AGENTS.md` / `CLAUDE.md`** | 仓库根的智能体操作指令 | 同源思路（agent-friendly Markdown），但作用范围是"仓库操作指令"，不是"知识库" |
| **Obsidian / Notion vault** | Markdown + frontmatter + 交叉链接 | OKF 把这套模式**形式化为可互操作规范** |
| **Dataplex / Unity Catalog / Collibra** | 企业数据目录 | OKF 是它们的**便携导出格式** |
| **Karpathy "LLM wiki"** | 概念模型 | OKF 把这个想法**形式化为可移植规范** |

OKF 明确把 `llms.txt` 与 `AGENTS.md` 列为先驱，但**作用范围不同**：OKF 解决"围绕数据与系统的结构化知识库"，而非"整站指令"或"仓库操作"。

## 5. 真实采用证据

- **`google/mantis`**（安全智能体项目）：内部使用 OKF v0.2 作为知识库格式
  - `reference/core/database.py` 定义 `okf_concepts` SQLite 表，字段含 `{concept_id, type, title, resource, tags, status, trust_tier, verified_by, generated_by, snapshot_id, sources, body_markdown}`
  - 提供 `export_okf_bundle` / `import_okf_bundle` 实现 Bundle ↔ 数据库的双向同步

## 6. OKF 启发的十条设计经验

值得在自家文档规范中借鉴的十条经验：

1. **小契约优先**：v0.1 仅 6 个字段，足以起步；不要过度设计
2. **信任是一等公民**：当 agent 开始大量生产文档时，必须显式记录 `generated` / `verified`
3. **绝对 Bundle 相对链接更稳**：`[/path](/path)` 比 `./path` 更耐目录迁移
4. **保留名克制**：只保留 `index.md` 和 `log.md` 两个，第三种就要慎重
5. **宽容解析**：未知 `type`、多余键、断链、缺 `index.md` 都不应被拒绝
6. **信任层级由消费者推导**：生产者不能自我声明 `trust_tier`，避免撒谎
7. **`stale_after` 用绝对日期**：易比较、易测试，胜过 TTL
8. **约定式标题**：用 `# Schema` / `# Examples` / `# Computation` 等**约定**而非硬约束，让人与 agent 收敛而不锁死
9. **Git 原生**：目录即 Bundle，可 diff / blame / PR，文档即代码
10. **"文档级验证"与"运行时证明"分离**：`verified` 是文档是否仍符合策略；`attester` 是某次运行是否产出预期值，两者都不可缺

## 7. 本技能与 OKF 的对应关系

| 维度 | OKF | 本技能（project-knowledge-hierarchy） |
|------|-----|--------------------------------------|
| 目录结构 | Bundle（领域无关） | 四层结构（项目/技术/资产/原始，强分层语义） |
| 保留文件名 | `index.md`、`log.md` | `index.md`（每个目录），暂未引入 `log.md` |
| Frontmatter 核心 | `type`（唯一必需） | `文档编号` + `标题` + `类型` + `状态` + `日期` + `作者` |
| 信任机制 | `generated` / `verified` / 推导 tier | `作者` 字段承担（无 agent 场景下足够） |
| 链接形式 | Bundle 相对 + 相对 | 相对路径（可升级为 Bundle 相对） |
| 来源记录 | `sources` 列表 | 正文末尾「## 原始资料」一节（来自原始层材料） |
| 一致性策略 | 宽容解析 | **强制每个目录有 `index.md`**（比 OKF 更严格） |

**核心差异**：OKF 是**通用、可互操作**的开放规范，本技能是**项目内部、强制分层**的工程化约定。

## 8. 借鉴 OKF 后本技能已采纳的增强

### 标准推荐字段（默认启用）

借鉴自 OKF 的两个核心元数据，AI **默认应在生成文档时一并输出**，除非用户明确表示不需要。

| 增强点 | 落地位置 | 借鉴自 OKF |
|--------|----------|------------|
| 新增推荐字段 `描述` | `templates/document.md` | OKF `description`，单句摘要利于索引与搜索 |
| 新增推荐字段 `标签` | `templates/document.md` | OKF `tags`，跨切面分类 |

### 扩展可选字段（按需启用）

仅在场景需要时启用。

| 增强点 | 落地位置 | 借鉴自 OKF |
|--------|----------|------------|
| 新增可选字段 `资源` | `templates/document.md` | OKF `resource`，规范 URI |
| 新增可选字段 `来源` | `templates/document.md` | OKF `sources`，承接「## 原始资料」约定 |
| 新增可选字段 `过期时间` | `templates/document.md` | OKF `stale_after`，新鲜度机制 |

### 结构层增强

| 增强点 | 落地位置 | 借鉴自 OKF |
|--------|----------|------------|
| 引入 `log.md` 保留名 | `references/directory-structure.md` | OKF §9，目录级变更历史 |
| 路由表指向本文件 | `SKILL.md` | 让 AI 在用户询问 OKF 时按需加载 |

## 9. AI 使用指引

- 当用户**询问"OKF 是什么"**或**"是否对齐 OKF"** → 加载本文件回答
- 当用户**要求"兼容 OKF"** → 在生成文档时同时输出 OKF 兼容字段（`type` / `description` / `tags` / `resource`）
- 当用户**要求"启用 log.md"** → 在每个目录添加 `log.md` 模板并按规范维护
- **默认行为**：生成业务文档时，AI 必须输出核心 6 字段 + 推荐 2 字段（`描述`、`标签`）
- 当**用户明确说"只要最小集"或"不要描述标签"** → 退化为仅 6 字段
- **不要**自动为所有文档启用 `资源` / `来源` / `过期时间` 三个扩展字段（按需启用即可）
